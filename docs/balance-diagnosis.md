# 余额不可用诊断

日期：2026-10-27。诊断基线：0.8.0 插件源码与本机 DSH Desktop / Harness 0.2.1-rc.2 随附服务实现。下文复现表记录修复前行为；0.8.1 修复状态见末尾。

## 已知现场信息

- 受影响用户已登录 DSH 账号，也配置了 API Key。
- 提示来自奶蛙气泡，原文为「余额暂不可用」。
- 尚未取得受影响电脑的 DSH 版本、本地余额接口状态码和错误码，不能据此断定为密钥、网络或上游服务的单一问题。

## 该文案实际意味着什么

前端 `src/pet.mjs:337–345,480` 将多类故障合并显示为同一文案：

| 本地接口结果 | 当前显示 | 可定位范围 |
| --- | --- | --- |
| `200 / NO_KEY` | 未配置 API Key | 该宿主无法解析固定的 `DEEPSEEK_API_KEY` 引用 |
| `200 / AUTH` | API Key 不可用 | 上游返回 HTTP 401 |
| `200 / UPSTREAM` | 余额暂不可用 | 上游返回其他非成功状态；原始 HTTP 状态被丢弃 |
| `200 / UNAVAILABLE` | 余额暂不可用 | 凭据读取异常、网络/TLS/超时、JSON 失败或金额解析失败 |
| 本地 `404/500`、非 JSON | 余额暂不可用 | 路由未注册、安装/服务组合或响应内容异常 |
| 前端请求异常或 12 秒超时 | 余额暂不可用；已有成功结果时可标为上次结果 | 浏览器到宿主的请求失败 |
| 本地 `403 / FORBIDDEN` | 当前连接不支持查询 | 本机同源访问限制 |

因此，已收到的文案不等同于「没配置 API Key」或「余额为零」。常规的无密钥和上游 401 分支显示其他提示，但存在后续故障时仍需以接口结果为准。

## 已复现的问题与边界

使用真实 `registerBalance()` 路由处理器及隔离的服务/fetch 替身复现，不读取真实密钥，不向公网发送请求：

| 场景 | 观测结果 |
| --- | --- |
| 官方 Key、标准余额响应 | 成功显示 `¥25.40` |
| 上游 HTTP 429 | 返回 `UPSTREAM`，无法从响应判断限流还是其他上游失败 |
| 请求超时 | 返回 `UNAVAILABLE`，超时类型丢失 |
| 合法 JSON 但金额为 `0E-16` | 被金额正则拒绝，返回 `UNAVAILABLE` |
| 账号服务可用但未注册 credentials 服务 | 整个余额路由不注册，本地 404 |
| 只登录 DSH、没有 API Key | 返回 `NO_KEY`，账号 `getBalance()` 调用次数为 0 |
| 正常 IPv6 回环访问 | 成功，不是所有 IPv6 连接都会失败 |
| 局域网地址访问 | 本地 403，属于现有访问边界 |
| 真实零金额 `0.00` | 成功显示 `¥0.00`，零余额不会自行触发不可用 |
| 成功读取后切换 Key | 一分钟缓存仍返回上一把 Key 的结果；缓存未按凭据隔离 |

科学计数法案例只证明解析器的兼容性缺口，并不证明受影响用户的官方 `/user/balance` 响应采用了该格式。DSH 账号余额服务明确支持这类十进制字符串。

现有 `tests/balance.test.mjs` 两项测试通过，但仅覆盖访问边界和金额解析，未覆盖服务注入、上游状态与请求失败。上述复现补充了这些诊断分支。

## 已确认的设计限制

1. `lib/balance.mjs:24,32,35` 强依赖 `webServer + credentials`，只读取 `DEEPSEEK_API_KEY`，固定请求 `https://api.deepseek.com/user/balance`。自定义凭据引用、第三方 API 地址以及 DSH 登录账号的 `deepseekAccount.getBalance(client)` 均未接入。
2. `lib/balance.mjs:36,40` 丢弃上游 HTTP 状态和异常类别；前端又把这些结果合并显示，现场无法自助区分原因。
3. 宿主请求超时为 10 秒；前端为 12 秒。网络较慢、代理或证书失败均可能进入同一不可用分支，尚无现场证据证明是哪一种。
4. DSH 本机凭据提供方优先读取存储值，再读取启动环境与环境文件回退。界面配置、启动终端与运行宿主若不属于同一环境，不能仅凭「已配置 Key」证明本插件解析到预期的 Key；不应回传密钥验证。

## 确定现场分支所需的最小信息

在出现异常的 DSH 页面开发者工具控制台执行以下读取，只返回本地 HTTP 状态和错误码，不输出余额或密钥：

```js
fetch('/naiwa-theme/balance.json', { cache: 'no-store' })
  .then(async r => ({
    status: r.status,
    code: (await r.json().catch(() => ({ code: 'NOT_JSON' }))).code || 'OK'
  }))
  .then(console.log)
```

另需记录 DSH 版本。`UPSTREAM` 仍需增加保留 HTTP 状态的诊断后才能区分上游限流、拒绝和服务错误；`UNAVAILABLE` 仍需区分凭据、超时、传输和解析阶段。当前源码没有这些信息，不能从同一提示反推出具体异常。

## 建议修正顺序

对比用户提供的可用实现后，应优先修复 Key 首尾空白、同步凭据异常后的永久失败和未覆盖凭据读取的超时，再拆分可操作的错误类别，保留脱敏的阶段与上游状态。账号余额是另一条独立功能路径，两份实现均未接入，不能用这一共同限制解释两者的可用性差异。数值格式兼容、凭据缓存隔离和缺少宿主服务时的明确提示也需分别处理。

初次对比仅诊断；随后按用户要求将下列三项修复纳入 0.8.1。

## 与用户提供的可用源码对比

参考包：`dsh-balance-reader-1.0.0.zip`；归档 SHA-256：`41b65218c90aecff995da6716ed67924d1ef113748a85c89086472e0c750b865`。包内 11 个文件的校验摘要均通过。来源记录标注提取自 EVA 插件 0.51.2；参考包自带 10 项测试全部通过。

参考包只解压到临时目录，逐项审阅 `balance-core.mjs`、`host.mjs`、`client.mjs` 及其测试后，使用同一组模拟凭据与响应进行两侧对照。未读取真实密钥或请求官方账户。

### 相同链路，已排除的推测

- 两者都在宿主使用 `credentials.resolve('DEEPSEEK_API_KEY')`，支持裸字符串和 `{ value }`。奶蛙没有把凭据对象直接拼成 `Bearer [object Object]`。
- 两者都固定请求官方 `https://api.deepseek.com/user/balance`，使用 Bearer 认证；浏览器都只访问各自本地余额路由。
- 两者都依赖 `webServer + credentials`，都没有查询 `deepseekAccount.getBalance(client)`。因此先前提到的账号服务缺失是共同的功能限制，不足以解释参考实现可用、奶蛙不可用。
- 标准 CNY 响应下，两者均正确显示测试金额；两者均拒绝 `0E-16` 字符串，所以该格式也不是参考实现独有的兼容优势。

### 已通过对照实验确认的差异

| 对照场景 | 奶蛙 0.8.0 | 参考实现 | 诊断意义 |
| --- | --- | --- | --- |
| Key 前面含换行，后面也有换行 | 未清理输入，构造请求头时抛出 TypeError，返回 `UNAVAILABLE` | `secretOf()` 去除首尾空白，正常读取 | 可直接复现「余额暂不可用」；不能证明现场 Key 含换行 |
| 第一次凭据读取同步抛错，第二次服务恢复 | 连续两次都失败，凭据服务只调用 1 次 | 首次失败，重试成功，凭据服务调用 2 次 | 奶蛙存在恢复后仍永久失败的缺陷 |
| 凭据读取 Promise 一直不返回 | 上游 fetch 尚未发出，宿主自己的 10 秒超时尚未启动 | 总超时包含凭据读取，返回 `TIMEOUT` 并释放并发状态 | 奶蛙前端可先在 12 秒时失败；后续查询仍共用未完成任务 |
| 上游 HTTP 429 | 返回 `UPSTREAM`，气泡显示通用不可用 | 返回 `HTTP_429`，客户端可显示限流提示 | 参考实现保留了关键的错误分支 |
| 钱包结构无效 | 返回 `UNAVAILABLE` | 返回 `NO_BALANCE` | 参考实现区分响应内容问题 |

未返回凭据的实验将参考超时缩短到 25ms，以免等待生产默认的 10 秒；奶蛙在观察期内保持 pending。关键结论同时由源码确认：奶蛙只有在凭据已解析、调用 fetch 时才创建 `AbortSignal.timeout(10000)`。

同步抛错的永久失败来自赋值顺序：`inFlight = (async () => { ... })()` 中，`credentials.resolve()` 在第一个 await 之前同步抛错，内部 finally 先把 `inFlight` 清空，然后外部赋值又把已经失败结算的 Promise 写回；未来每次读取都提前返回这个 Promise。参考实现将操作延迟到 Promise 链中执行，并在外层 finally 按任务身份清空，从而可以重试。

首部空格的实验也观察到奶蛙发送 `Bearer` 与 Key 之间的多余空格；测试端按精确 Bearer 值拒绝，参考实现通过。这依赖服务端容忍度，不能据此断定官方接口会拒绝所有首部空格。首部换行导致请求头校验失败则不依赖服务端。

### 不应直接照搬的部分

参考包只检查 Host/Origin；奶蛙另外检查实际 socket 对端并拒绝转发头。去掉 socket 元数据的模拟请求在奶蛙抛出 TypeError，参考包可处理，但本机随附 DSH WebServer 传入的是带 socket 的 Node IncomingMessage，暂无证据证明受影响用户缺失该字段。可修正空值处理以避免抛错，不应为了兼容而直接移除现有访问边界。

参考包的缓存同样不按 Key 隔离，且依然不接受科学计数法字符串；这些共同问题不应当被当作已通过替换解决。

### 当前结论

现在已从泛化故障范围缩小到若干可直接复现的实现差异，尤其是输入清理、同步异常重试和凭据读取超时。仍需现场接口的 `status/code` 或修复后验证，才能确认受影响用户实际命中的分支；不能将离线对照结果表述为已确认其真实 Key、网络或宿主状态。

## 0.8.1 修复状态

- 清理 Key 首尾空白，同时保留裸字符串和 `{ value }` 的兼容。
- 凭据读取延迟到 Promise 链中执行，所有结束路径在外层 finally 按任务身份释放 `inFlight`，同步抛错后也能重试。
- 10 秒总超时从读取开始计时，通过取消竞速约束凭据解析、fetch 和 JSON 解码；忽略取消的依赖不会占住后续重试。各异步步骤结束后检查取消状态，阻止迟到请求或结果污染新缓存。
- 超时返回不含原始异常的 `TIMEOUT`，气泡显示明确超时提示；卸载取消未完成操作。

新增 10 项回归测试，与原有两项余额测试一起验证上述问题、并发缓存、失败后的恢复和宿主路由接线。原有本机访问限制、凭据引用、官方 API 地址、钱包口径和成功缓存时间保持原约定。其他诊断事项未纳入此次三项修复。
